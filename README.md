# Сайт психолога Шамиля Габзалилова

Статический сайт для ознакомления взрослого клиента с условиями перед первой консультацией. HTML и один CSS-файл. Нет JavaScript, сборщика, npm-зависимостей, серверной части, форм, оплаты на сайте, аналитики и внешних ресурсов.

## Файлы сайта

- `index.html` — главная страница со всеми правилами и контактами.
- `assets/css/styles.css` — оформление для телефонов, компьютеров и печати.
- `legal/therapy-contract.html` — терапевтический контракт и правила.
- `legal/terms.html` — условия оказания психологических консультационных услуг.
- `legal/privacy.html` — незавершённая политика обработки персональных данных.
- `legal/drafts/personal-data-consent.html` и `legal/drafts/special-personal-data-consent.html` — недействующие черновики отдельных будущих согласий.
- `404.html` — страница неизвестного адреса.
- `docs/content-version.md` и `docs/legal-change-log.md` — версия и история изменений.
- `.nojekyll` — пустой служебный файл для публикации без Jekyll. Не удалять.

Можно открыть `index.html` двойным нажатием. Для полной проверки ссылок и заголовков безопасности нужен локальный HTTP-сервер или опубликованный сайт. Ничего собирать перед публикацией не требуется.

## Что нужно заполнить до юридического запуска

Техническая публикация не означает, что сайт уже готов для принятия клиентом условий оплатой. Владелец должен заполнить и утвердить юридический статус, обязательные реквизиты, данные оператора и необходимые разделы политики ПДн. Места обозначены комментариями `LEGAL_TODO`. На страницах виден статус незавершённости.

Контактные ссылки ещё не предоставлены: все пять кнопок недоступны, это объяснено посетителю. Нельзя просто убрать предупреждения о незавершённости, не заполнив данные.

Согласия в `legal/drafts/` не действуют, не подписываются и не доступны из основной навигации. Они будут подписываться отдельно после будущего подключения сервиса электронной подписи. Файлы находятся в публичном репозитории и доступны по прямым адресам — скрытие из меню не является ограничением доступа.

Календарь и форма записи сейчас отсутствуют. Их будущее добавление потребует отдельного решения и пересмотра модели обработки данных. Функции электронной подписи сейчас тоже нет.

## Как изменить имя

Откройте нужные HTML-файлы и замените «Шамиль Габзалилов» в видимом тексте, заголовке вкладки (`title`), шапке и подвале. На главной имя и фамилия разделены `<br>`. При переименовании обновите также инициалы «ШГ». Не меняйте автоматически текст других документов без согласования.

## Как добавить контакты

В `index.html` найдите комментарий `CONTACT_CONFIGURATION` в разделе `id="contact"`. Там находятся пять предусмотренных ТЗ маркеров контактов. Их значения не используются как ссылки и не показываются посетителю.

Для каждого полученного реального контакта:

1. Замените соответствующую кнопку `<button ... disabled>...</button>` на ссылку `<a class="button contact-button" href="подтверждённый адрес">название канала</a>`.
2. Для телефона в `href` укажите `tel:` и реальный номер в международном формате. Видимым текстом может остаться «Позвонить».
3. Если нужно открытие в новой вкладке, добавьте `target="_blank" rel="noopener noreferrer"`.
4. Удалите заполненный маркер из комментария. Оставшиеся каналы держите недоступными и уточните пояснение под кнопками.
5. Проверьте каждую добавленную ссылку со смартфона. Ссылка должна вести в ваш аккаунт, а не просто на главную мессенджера.

Адрес меняется в одном месте — в `href` соответствующего канала на главной странице. Не вставляйте виджеты и скрипты мессенджеров. Не используйте реальные данные клиентов при проверке.

## Как изменить стоимость

Сейчас цена не публикуется по ТЗ. Формулировка о сообщении стоимости находится в разделе «Запись на консультацию» на главной, в терапевтическом контракте и условиях услуг. Если позднее владелец решит публиковать цену, согласуйте единый текст во всех этих местах. Не подставляйте цену предположительно.

## Как изменить правила или юридический документ

1. Найдите заголовок нужного раздела в `index.html`.
2. Измените соответствующий текст и в `legal/therapy-contract.html`, а если правило связано с заказом, оплатой или организацией встречи — также в `legal/terms.html`.
3. Для сведений о данных проверьте также `legal/privacy.html`.
4. При существенном изменении увеличьте номер редакции, обновите дату в затронутых документах, подвалах и блоке документов главной страницы.
5. Обновите `docs/content-version.md` и добавьте запись в `docs/legal-change-log.md`: дата, редакция, что изменилось.
6. Откройте страницы и сравните формулировки. Изменение исходника не является само по себе юридическим утверждением новых условий.

В каждой HTML-странице даты и редакции — обычный текст. Редактируйте только нужные текущие значения; исторические записи в журнале не переписывайте. Старую версию можно увидеть через историю Git.

## Как опубликовать изменения

1. Измените файл и сохраните его.
2. Сделайте commit — сохраните именованную версию изменений.
3. Выполните push в `main` — отправьте её в GitHub.
4. Дождитесь завершения сборки Pages в разделе Actions и проверьте публичный сайт.

Из папки проекта команды выглядят так:

```sh
git status
git diff --check
git add index.html assets/css/styles.css legal docs README.md 404.html robots.txt .nojekyll
git commit -m "docs: update consultation information"
git push origin main
```

Перед `git add` убедитесь, что в перечисленных каталогах нет приватных файлов. Не добавляйте всё содержимое общей рабочей папки.

Для первоначальной публикации, если репозиторий приходится создавать вручную, создайте пустой публичный репозиторий `shamil-psychologist-site` в своём GitHub-аккаунте, без автоматически добавленных README и лицензии. Скопируйте его HTTPS-адрес. Затем в папке этого проекта выполните `git remote add origin` с этим адресом и `git push -u origin main`. Если origin уже настроен, повторно добавлять его не нужно: проверьте `git remote -v`. Отдельно отправьте готовый тег командой `git push origin site-v1.0.0`.

Не перезаписывайте выпущенный тег `site-v1.0.0`: он фиксирует первую проверенную версию. Для следующего релиза создайте новый тег после проверок.

## Как подключить GitHub Pages

Repository → Settings → Pages → Build and deployment → Deploy from a branch → main → /(root) → Save.

Здесь `/(root)` означает корень репозитория, а не каталог с именем root. `index.html` должен лежать непосредственно в корне. HTTPS включается в Settings → Pages → Enforce HTTPS, если переключатель доступен.

Если имя репозитория изменится, обновите абсолютный префикс `/shamil-psychologist-site/` в `404.html`. Он нужен, чтобы страница 404 работала даже для неизвестных вложенных адресов. Остальные страницы используют относительные пути и работают внутри проектного URL GitHub Pages.

## Приватность и индексация

При загрузке HTML-страница запрашивает только собственный CSS. CSP запрещает скрипты, формы, фреймы и фоновые соединения. Внешние контактные сервисы открываются только после нажатия добавленных ссылок.

Гарантия отсутствия cookie относится к коду сайта. Хостинг и внешние каналы связи имеют собственную инфраструктуру; их обработку необходимо отдельно учесть при юридическом запуске. Это не обещание, что сервер хостинга не получает технические данные HTTP-запроса.

`noindex, nofollow` на страницах и `Disallow: /` в robots.txt добавлены по ТЗ. Это не пароль и не ограничение доступа. robots.txt проектного сайта лежит внутри адреса репозитория, тогда как роботы обычно проверяют robots.txt в корне домена. Кроме того, запрет обхода может мешать прочитать noindex. Не считайте индексацию абсолютно исключённой. Репозиторий и сайт публичные.

## Проверка после изменений

- Откройте главную и все юридические страницы, пройдите по внутренним ссылкам.
- Проверьте ширины 360, 390, 430, 768, 1024 и 1440 px, отсутствие горизонтальной прокрутки и читаемость текста.
- Пройдите по ссылкам клавишей Tab: фокус должен быть виден. Первая ссылка позволяет перейти к содержанию. Недоступные контактные кнопки намеренно пропускаются.
- В DevTools → Network очистите журнал, перезагрузите страницу и убедитесь, что нет запросов к сторонним доменам. Не нажимайте внешние ссылки во время этой проверки.
- Проверьте консоль на ошибки CSP и ресурсы с ошибкой 404.
- Сравните главную, контракт и условия, чтобы одинаковые правила не расходились.
- Выполните `git diff --check` и `git status`.

## Никогда не помещать в репозиторий

- Данные клиентов, переписки и документы клиентов.
- Записи консультаций и медицинские данные.
- Пароли, API keys, токены и другие секреты.
- `.env`, cookie-файлы и реальные приватные файлы.

Удаление секрета из последней версии не удаляет его из истории Git. Поэтому проверять состав нужно до коммита и отправки. `.gitignore` — вспомогательная мера, а не защита от всех ошибок.
